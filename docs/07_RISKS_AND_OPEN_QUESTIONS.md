# 07｜风险、暂未验证能力与后续扩展

## 1. 必须正视的风险

| 优先级 | 风险 | 后果 | 最小缓解方法 |
|---|---|---|---|
| P0 | LLM 擅自添加设备/物理线 | 拓扑事实错误 | Schema + 关系类型校验 + 歧义警告 |
| P0 | Desktop 回导丢失自定义 XML cell | 用户劳动成果被破坏 | 以最新原始 XML 为事实源、定向修改/保留未知 cell |
| P0 | 使用全图 ELK 重排进行局部修改 | 手工调整全部失效 | 锚点插入、锁定几何坐标、冲突显式返回 |
| P0 | 压缩页/多页兼容性不足 | 回导失败、页面丢失 | 安全解压、明示 V1 范围、不可支持时拒绝 |
| P0 | 上传 XML/内容注入 | 服务器安全问题 | 禁用外部实体、限制解压/文件大小、内容安全编码 |
| P1 | Graph 与 XML 的对象 ID 失配 | 修改错对象、连线断裂 | 稳定映射 + 版本差异检测 + 导入确认 |
| P1 | 网络设备图标欠专业 | 成图接受度差 | 先用内置安全形状，后续增加类型图标库 |
| P1 | 复杂组和正交连接拥挤 | 文字/线条遮挡 | 两类模板、预留空间、必要时 Desktop 手工精修 |
| P1 | 外部 LLM 处理内部 IP/拓扑 | 信息泄露 | 私有模型/脱敏、最小权限、默认不记原文日志 |

## 2. 确认之前不得写成“已经支持”的能力

- 任意第三方复杂 `.drawio` 完整无损回读（本版先支持由本项目生成的文件）。
- 所有 ELK.js 场景中的节点原位置冻结、任意复杂正交无交叉线路由。
- `.drawio` 导入到其他软件的完全等价编辑。
- Windows draw.io Desktop 人工打开/保存的兼容性（必须实际测试）。
- 从照片无误识别连接端点；现有两张参考照片仅用于人工核对外观。

## 3. EDDX 的状态

用户曾提出把 draw.io 替换为亿图图示 `.eddx`，但随后明确只做评估、**不改变当前方案**。

- 当前实现目标仍然是 Windows draw.io Desktop + `.drawio`。
- 是否能通过 VSDX 中转进入亿图图示、线条连接点是否保留、程序化原生 EDDX 读写是否可用，均属另一个专项技术验证，不进入 Codex 当前任务。
- 将来若切换编辑器，应单独设计 `FileAdapter` 边界并做往返兼容性测试，不能只重命名文件后缀。

## 4. V1 后续可扩展项（按优先级）

1. Excel/CSV 设备与关系批量导入。
2. 图标库、主题、常见网络/业务架构模板。
3. 高密度拓扑局部重排和线路径优化。
4. Windows 本地助手实现“自动下载/启动/文件保存同步”，需单独权限与冲突处理。
5. PPTX/VSDX 导出及其他编辑器兼容性评估。
6. 多模态模型解析图片，必须给低置信关系留人工确认通道。
7. 多人协作、审计权限与企业部署能力。

## 5. 执行者需要记录的设计判断

若发生范围外要求、 Schema 不足、XML 无法无损修改或布局冲突，Codex 应在 `IMPLEMENTATION_REPORT.md` 的“问题与决策”记录：

- 问题与复现方式；
- 当前方案支持什么、不支持什么；
- 可选解决方式、对数据/接口兼容性的影响；
- 推荐的最小修改及需要用户批准的事项。

不要因为是 AI 项目，就把工作流难点全部交给 LLM 再生成一次全图。
